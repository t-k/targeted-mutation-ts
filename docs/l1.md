# L1 grammar and candidate contract

L1 version 1 uses a single declaration or an empty file. Its lexical rules are defined over UTF-8, with ASCII identifiers and punctuation. The module dialect permits the initial `export`. A JSX initializer is available only in TSX.

```text
file        ::= trivia (declaration ";"?)? trivia EOF
declaration ::= "export"? "const" identifier "=" (parameter "=>" result | result)
parameter   ::= "(" identifier ":" "number" ")"
result      ::= comparison | element
comparison  ::= atom (operator atom)?
atom        ::= identifier | decimal | "(" comparison ")"
operator    ::= "<" | "<=" | ">" | ">="
element     ::= "<" jsx-name attribute* "/" ">"
attribute   ::= jsx-name "=" (jsx-string | "{" comparison "}")
```

The ordinary lexical mode skips spaces, tabs, LF, CRLF, ASCII line comments, and block comments. A line break, including one in a block comment, is forbidden between the parameter's closing parenthesis and the arrow. Identifiers have the ASCII structure of JavaScript identifiers without escapes and exclude reserved words. Declaration and parameter names also exclude `eval` and `arguments`. JSX names allow hyphens after the first character and have no reserved-word restriction. An unsigned decimal is an ASCII digit sequence with no leading zero except the literal zero. JSX attribute strings have matching single or double quotes and may contain UTF-8, including comparison punctuation. In JSX tag mode only spaces, tabs, and line endings separate tokens. In an attribute expression the ordinary lexical mode resumes.

The fast path accepts at most 1,048,576 source bytes, a depth of 64 parenthesized expressions, and 4,096 candidates. Byte spans are half-open and relative to the original file. A comparison candidate contains the rule version, original operator, replacement operator, operator span, and both operand spans including syntactic parentheses. Candidates appear in source order of operator start, including nested comparisons. EOF must be reached before publishing the candidate buffer.

The versioned boundary rule is `comparison-boundary/v1`. Each of the four operators maps to the same strictness family with the equality bit toggled. Scope restrictions and UTF-8 validation precede the recognizer. After a fast-path miss, TMT parses the entire file with Yuku and converts AST and token positions back to byte offsets. A diagnostic discards all candidates for that file.

After checking the fallback diagnostics, TMT inspects the token kinds before reading Yuku's lazily decoded AST. Files without a relevant comparison or JSX logical token need no AST for mutation extraction. Analysis maps ordered candidate byte offsets to UTF-16 line and column positions in one pass. The native scan uses 16-byte NEON or SSE2 blocks for ASCII without line endings. The scalar path handles other bytes and platforms. A checked Low★ byte reader recognizes U+2028 and U+2029 for both the grammar and the position scan.

## Verification and measurements

`TmtReference.fst` parses lexer outputs into a complete AST for L1. Its compact interpretation computes operand spans and ordered candidates without expression trees. F★ checks equality of the two interpretations for every token sequence, including failure, and checks acceptance for all ASTs admitted by the independently written bounded grammar predicate and printer. The verified Low★ routines used by the native parser implement bounds-checked reads, maximal character-class scans, operator recognition, and indexed candidate writes. These contracts start with a live input buffer of the supplied length and an allocated output buffer of the supplied capacity.

`TmtParser.fst` implements the actual AST-free native grammar, recursive descent, lexical modes and EOF handling. Its extracted C runs in the ordinary Node-API entry point. Low★ checks termination, live-memory preconditions, bounded buffer accesses, the candidate count on success, consumption of the entire input buffer on success, and zero published candidates on failure. The C adapter supplies distinct buffers and their real lengths. A typechecked example evaluates the reference on the exact TSX token sequence and checks the candidate span and rejection of a malformed suffix.

`native_operator_backpatch` connects the byte-level operator scanner and native candidate write to the reference interpretation of a comparison. Given correct child candidates, operand spans and a reserved slot, it proves the output slice equals the reference candidate list including byte spans and order. The correspondence between the full byte-level parser and the F★ reference token model still requires proof of these premises throughout parsing and tokenization. Buffer allocation, UTF-8 validation, C compilation, and Node-API marshalling remain in the trusted execution boundary. `candidateBytes` measures candidate heap allocations in the native adapter. The fixed stack allocation and JavaScript output objects have separate storage. The AST counter is zero by construction for this native parser.

The corpus report checks every returned candidate field and diagnostic status. The TypeScript corpus is the sparse checkout of `tests/cases/compiler` at the reported revision, including intentional parse failures and raw encoding fixtures. For a fallback file the product currently invokes the reference parser itself, so independent parser agreement is measured on fast files. None of the Vite and Preact files used the fast grammar. Twenty compiler fixtures used it and produced no comparison candidates. The controlled TS/TSX fixtures exercise the nonempty native output. A performance claim needs a broader grammar and a native-to-native benchmark under comparable conditions.
